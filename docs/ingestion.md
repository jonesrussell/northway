# Bounded feed ingestion

Implemented for #12: one explicit feed-document acquisition, metadata parsing, tenant-scoped SQLite ingestion, conditional validators and persistent admission/recovery. No source has been activated by this implementation. Catalogue files are not runtime configuration. There is no crawling, article-page traversal, image/enclosure fetching, provider call, scheduling timer or feed HTTP endpoint.

## Operator boundary and execution

`northway ingest once --database PATH --tenant UUID` performs at most one due poll. It requires exclusive database ownership, so stop `serve` first. It does not create a database or migrate implicitly. It reports only status, HTTP status, item count and bytes; publisher bodies, URLs, validators and transport errors are not printed. Idle, busy and budget-deferred work is distinguishable from a failed poll. There is no retry flag or URL flag.

The hash-pinned [local personal-news profile](real-news-pilot.md) now has an explicit operator provisioning command. Lower-level source provisioning remains an internal local-operator seam, matching existing corpus provisioning. `ConfigurePoll` takes an exact existing source URL, explicit approved/enabled flags, minimum interval and response allowance. Neither existing `sources.enabled` nor an approved planning manifest enables collection: a separate poll-policy row must be provisioned. No public caller or API key can configure or claim collection. Permission/selection decisions must be recorded in the reviewed catalogue before the operator enables its corresponding policy; #46 remains open. This PR invokes provisioning only on synthetic temporary databases in tests.

The service and store interfaces can be wired into the future in-process scheduler without a second SQLite owner. Opening storage, starting `serve`, requesting a panel or querying a cache does not invoke the collector. Scheduling and deployment wiring remain separate work.

## Transport and parsing

- HTTPS only, port 443, no credentials, query or fragment in configured source URLs. Fresh DNS answers must all be public addresses; pin one address for the connection and verify TLS against the original hostname. Block loopback, private, link-local, multicast, documentation and selected special-use ranges, including mapped IPv4 and IPv6 transition ranges. No environment proxy, redirects, alternate-address retries, connection reuse or HTTP/2 retry path. The narrow pilot intentionally rejects some otherwise legitimate endpoints.
- One 15-second fetch deadline, within a two-minute claim lease, with bounded TLS/header deadlines and 16 KiB response headers. A fresh transport is intentional for DNS pinning and avoiding implicit retries at this low polling rate. The scratch image receives its CA bundle from the existing digest-pinned builder; no custom publisher certificates are trusted in production.
- Ask for identity encoding and reject compressed responses; no decompression bomb is possible in this path. Read at most the reserved body allowance, at most 2 MiB. A body exactly at that ceiling is conservatively rejected rather than reading an extra uncharged byte to prove EOF. This is an application body limit, not a bound on TLS/TCP framing or kernel buffers. Non-200/304 bodies are not parsed.
- Pass only already-fetched bytes to `gofeed v1.4.2`; never use its URL-fetching API. Before parsing, validate UTF-8 XML, reject DTD/directive/entity declarations, cap nesting at 32, tokens at 60,000 and feed entries at 1,000. RSS 2.0 and Atom only (no RDF/RSS 1.0), no JSON Feed, HTML discovery, sitemap or browser fallback. Cancellation is checked during preflight, reads and item conversion. Non-XML processing instructions, including stylesheet references, are inert and allowed without fetching their targets. The token and entry ceilings are independent; a complex valid feed may reach the token ceiling before 1,000 entries and be rejected.
- Retain stable upstream item ID (falling back to the item URL), title, original HTTPS link and optional publication timestamp; publisher attribution comes from the configured source. Bodies/descriptions/enclosures are discarded. Keep unknown dates unknown. Reject invalid or oversized required metadata instead of silently advancing past it. Identical repeated IDs are coalesced; conflicting duplicates reject the whole document.

Item URLs are never fetched. Their canonicalization preserves path, query ordering and scheme semantics, removing only fragments. North Cloud's forced scheme upgrade and trailing-slash normalization are not imported. An existing natural-key match retains its original ID; otherwise a source/item-derived opaque UUID is separate from its content hash; URL/date/title changes update the same item and create a metadata version. Cross-source syndication deduplication belongs to retrieval #13.

## Transaction and recovery rules

All relational SQL is in `db/queries/ingest.sql`, generated by sqlc; migration 5 adds poll policy, attempts and cursors without enabling existing sources. The shared serialized immediate-transaction path claims work before network I/O. Claim IDs fence late workers; reconfiguration, disabled source access, changed approved URL or an expired lease prevents completion.

The final transaction updates items, content versions, FTS, corpus revision, validators and last-success state together. A storage failure rolls all of them back. A 304 updates successful-check time and preserves absent response validators; an unsolicited 304 without prior validators is rejected. An unchanged 200 does not rewrite article/version/FTS rows, refresh article observation times or invalidate query caches. A 200 that removes validators clears the old validators after commit.

Every admitted poll persists its next eligible time before the request. Failures have fixed status categories; they never automatically re-enable sources or trigger retries. Publisher Retry-After, max-age/Age and Expires can extend the hold. Valid delta-seconds and HTTP dates are honored, including long successful-200 cache lifetimes. Malformed Retry-After/max-age fields conservatively defer seven days; unrepresentable positive lifetimes hold until operator review. An explicit local-operator `ResetPollSchedule` seam can clear a reviewed hold without changing approval or refunding work. It preserves minimum spacing from the last attempt; an in-flight source is marked `reset` and its worker is fenced, while the pending reservation stays charged until lease recovery. Ordinary ConfigurePoll preserves holds. Never reset a publisher hold routinely to evade its limits. A `no-store` response is deliberately rejected (`no_store`), with no new metadata persisted and a full reservation charged; derived-metadata retention is not assumed permitted. Multiple Cache-Control header fields are considered together. Cancellation attempts a separate five-second settlement; an interrupted process leaves a conservative reservation. On the next claim, expired pending work becomes abandoned and cannot publish old results.

## Resource and fairness limits

The whole database shares one active claim, 180 attempts and 64 MiB of body-byte reservations per rolling 24 hours, across tenants and panels. Individual source intervals are at least one hour and can be up to seven days; source-specific tighter policy wins. The five-source bootstrap therefore remains at most 120 hourly attempts without manual reconfiguration. The ten broader candidates remain disabled; the 180 ceiling is not approval to add sources.

Reserve the source's full response allowance before I/O. On success, settle actual body bytes; errors and crashed attempts retain the full allowance because transfer accounting may be uncertain. Attempts remain counted even for 304 or failure. The rolling retention starts at settlement, or lease expiry for abandoned work, so accounting is conservative across restarts. Closed accounting rows are pruned only after their full 24-hour window. There is no daily reset that can double a short-window allowance.

For each operator's tenant, select due sources in stable source-ID order after the persisted cursor, wrapping once. Held, disabled and not-yet-due sources do not pin the cursor. Admission advances it even when the request later fails; either byte or attempt exhaustion leaves it unchanged, preserving the next eligible source. The global budget is shared, but fair scheduling between tenants is not promised by this initial single-tenant operator command.

Guardrails bound configuration to 100 source policies across the database, parsing to 1,000 entries per response, and stored admission to 5,000 current items / 10,000 versions per source. Exceeding a corpus cap rolls back the poll, records `corpus_full` at full charge and makes the command fail nonzero. It requires retention/operator action; it does not delete evidence, report discarded items as ingested, or accept a partial feed. These row/work caps are not the proposed 256 MiB storage allocation or a measured Pi footprint. Retention, complete disk/WAL limits, actual-device workload/recovery and scheduled operation still belong to #20/#36.

If polling adopts an existing item with the same tenant/source/origin identity, it preserves the item ID but clears any current stored body and records a metadata-only version. Historical versions are not purged by ingestion; retention remains separate.

## Verification and limits

Tests use authored fixtures, local verified-TLS servers and temporary real SQLite files. They cover RSS/Atom metadata, unknown dates, identity fallback/conflicts, malformed/oversized/deep XML, mixed public/private DNS, redirects, untrusted certificates, pinned connections, conditional 200/304, stalled/partial body reads, cancellation, operator/tenant boundaries, atomic rollback, real SQLite disk-full simulation, unchanged-item writes, URL-only versions, global concurrent claims, byte/attempt exhaustion, holds/cursors, restart and stale-worker fencing. CLI tests prove it cannot accept an arbitrary source URL or enable collection.

Run `make check race vuln`, `go test ./internal/fetch -run '^$' -fuzz FuzzParse -fuzztime=20s`, and `go test ./internal/fetch -run '^$' -bench BenchmarkParseLargeFeed -benchtime=3x -benchmem`. The 870-entry synthetic feed benchmark measured about 58 ms/op and 20.4 MB allocated/op on the workstation (three iterations, 2026-08-31); allocation is not peak resident memory or Pi capacity. Parser performance, feed usefulness, public-network reachability, TLS trust-store maintenance and actual Pi recovery remain distinct evidence questions.

Migration is forward-only. Old binaries reject schema 5. Rollback requires a coherent pre-migration backup or a forward fix, not deleting the migration or copying a live database without its WAL. No existing runtime data was migrated during development. See [the import ledger](migration.md) for North Cloud provenance and [source policy](content-sources.md) for activation constraints.
