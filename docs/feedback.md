# Explicit feedback events

Implemented in #16 for NW-002 and NW-007. `POST /v1/feedback` requires `feedback:write`; it does not require or confer `feeds:read`. The feature service validates bounded event fields, then the SQLite adapter authorizes the principal and uses one immediate write transaction for snapshot membership, current source/feed access, replay/reversal checks, event append and feed revision increment.

An event names an available owned snapshot and an article still visible in it. The corpus row need not exist: immutable snapshot evidence establishes membership. A guessed ID, other tenant, expired snapshot or revoked source/feed returns not_found, including otherwise identical replay. Rights/availability take precedence over the event replay promise.

Events are append-only and unique by (tenant, event_id). Identical replay returns 204 without another revision increment, even after its original event has been reversed. Changed payload on an available owned snapshot conflicts. `undo` must reference a non-undo event in the same tenant, snapshot and article; a missing target is not_found, a mismatched/previously reversed target conflicts. A partial unique index permits only one reversal of each tenant event. Concurrent duplicate submissions and reversals serialize through the same transaction; affected-row checks reject ignored inserts/updates, with full rollback.

Each new event increments the feed revision once, atomically invalidating new-query cache identity. Existing snapshot GET and original query replay keep their original evidence, subject to current access. Save, dismiss and less_like_this are recorded preferences, not a new retrieval policy: no ranking model consumes them yet, no source selection changes, and no cross-customer learning occurs. An undo records the reversal; it does not delete the audit event or reapply older events. Client display state and applying feedback to future ranking are explicit later work.

Migration 7 is additive and forward-only. Events retain opaque article/snapshot IDs without foreign keys to deletable corpus/snapshot rows, so seven-day snapshot cleanup does not erase saved feedback evidence. The feed and reversal foreign keys remain tenant-composite. Personal-pilot maintenance deliberately does not age out events; future tenant export/deletion must preserve reversal relationships and define backup expiry. The whole database remains subject to the 256 MiB admission ceiling. No new runtime dependency is added.

Validation: real SQLite concurrent duplicate/reversal tests; injected ABORT/IGNORE failures on revision updates; cancellation, unavailable membership, deleted corpus, revoked-source and expired-snapshot cases. Real HTTP tests exercise two tenants with shared corpus/event IDs, feedback-only/read-only scope separation, duplicate/conflicting payloads, undo-of-undo and current access checks. Authored metadata and disposable local keys only; no deployed traffic or provider work.

An event overlapping in-flight retrieval can invalidate that claim. The [API recovery policy](api.md#queryfeedback-overlap-and-recovery) specifies last-snapshot display and a deliberate user refresh; no automatic replacement key or weakened revision fence is introduced.
