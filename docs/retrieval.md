# Deterministic personal-feed retrieval

Implemented for #13 / NW-001, NW-004, NW-005 and NW-006. `query.NewService(store).Query` combines existing durable query claims/cache with bounded metadata retrieval, deterministic selection and immutable evidence. `Get` reads the stored result and rechecks access. `Snapshot.Response(requestID, now)` produces the draft feed-snapshot shape. This is an internal Go service and tested response projection, not an installed scheduler, product HTTP route, public provisioning API or Claudriel panel. No provider SDK, model call, crawl or new dependency is added.

## Saved selection and context

The local operator first creates a tenant, sources, feed and source memberships, then calls `ConfigureFeedPreferences` with `feed.Preferences`. All configured sources must already be attached, enabled and owned by that tenant; this operation cannot approve or enable collection. Existing feeds have no retrieval policy after migration and fail explicitly until configured, rather than inferring interests or silently widening source selection. Only the configured subset of attached sources is eligible.

Preferences contain an ordered list of one to five categories (`development`, `entertainment`, `canada`, `first_nations`, `world`), up to 100 source rules, a publisher cap of one or two, at most 20 excluded literal title tokens and `use_context`. Each rule supplies a source UUID, explicit publisher-group identifier and one or more selected categories. Sections of one publisher must share a group, such as Corus; separate endpoints are not independent publishers. Source-level membership/revocation and preferences are checked together. Preference changes atomically increment the saved feed revision and invalidate cache identity.

Default personal feeds use `use_context=false`: retrieve recent eligible items regardless of an active workspace's technologies or generic intent text. This is an explicit saved mode, not a language-model guess. A feed with `use_context=true` uses up to eight distinct literal terms, taking technology names, then focus, then intent; common request words and category labels are omitted. A broad request with no remaining terms uses recency. The request schema stays unchanged and its full validated digest still partitions caches even when some context is ignored. A focused personal search can be provisioned with context enabled; per-request search-mode switching and preference CRUD are later work.

The lexical baseline does not interpret negation, version ranges or natural-language exclusions. Versions never establish compatibility. Put exclusions in saved policy; they use FTS5 literal title-token matching and its Unicode tokenizer, not raw MATCH syntax or substring filtering. Nothing ranks by identity, inferred politics or inferred Nation/community membership.

## Candidate and selection bounds

One consistent read transaction checks the claimed request, feed/corpus/entitlement revisions and tenant before reading candidates. Each category reads at most 51 metadata rows: 50 candidates plus a truncation sentinel. SQL applies tenant, selected/enabled source, age, future-date, literal title-match and exclusion filters before the cap. Only titles are searched; stored legacy article bodies cannot influence this feed-only evidence path. There are at most five category reads and 250 retained candidates. A five-second request deadline bounds all local work, including claim/finish and database waits; failed work receives a separate two-second cleanup deadline. There are no automatic retries or external calls.

Known publication time controls age. When it is null, observation time controls eligibility and published_at remains null, with an explicit warning that observation does not prove recent publication. Future publication/observation times are ineligible. A recent publication is eligible even if first observation predates the requested age window. Eligibility is frozen relative to the durable claim's time.

The shortlist is the 50 most recent eligible rows per category, ordered by effective timestamp then article UUID. Within that shortlist, rank by the count of literal context tokens appearing in the headline, then effective timestamp, then UUID. There is no cross-tenant BM25 score dependency, semantic model, title-similarity clustering or promise that a globally best older match is in the bounded window. A capped window emits a warning.

A single-category feed returns up to the requested limit (1–20), subject to the publisher cap. A mixed feed considers categories in saved order and selects one item per category, up to the request limit. It tries the next candidate within that category when the first conflicts with a used article ID, canonical URL or shared publisher cap. Empty slots are not redistributed. If limit is smaller than the category count, only the first categories are requested and a warning explains the limit. Earlier categories win conflicts; changing that priority requires a saved revision.

Canonical URL comparison lowercases the host, removes default HTTPS port/fragments and normalizes an empty path to `/`; path escaping and query parameters are preserved. Tracking-parameter stripping and content-based deduplication across distinct URLs are not claimed. Every retained article ID and canonical URL occurs at most once. Missing categories produce explicit warnings and fewer items, never unrelated substitutions.

## Evidence, coverage and durable state

Finalization rechecks the original deterministic corpus/feed/entitlement revisions and current item versions in the existing serialized transaction. A conflicting arrival or policy change fails the query; it does not rerun selection automatically. The older paid-completion seam still permits unrelated corpus arrivals after a provider attempt. Snapshot items, details, completed claim and zero-cost settlement commit together or all roll back.

Snapshots freeze original IDs, title, link, publisher attribution, publication/observation times, category and explanation. Evidence is the stored headline with `source_metadata` basis. Summary explicitly says only headline metadata is available; the explanation says selection is unverified beyond that evidence. No body, private context, technology-version assertion, invented source or fetched article-page content is stored as evidence. Display titles/source names are Unicode-safely capped to the unchanged schema (500/200 characters); evidence retains the original headline. The HTTP/UI adapter must still render untrusted text safely.

Source coverage records the original selected source IDs and the last known successful persisted poll. Its freshness window is twice that source's configured polling interval, not an ingestion guarantee. A source without successful poll state has no current coverage. Response projection ages those stored deadlines using the current clock and rechecked access; it cannot claim newly successful polls that occurred after the snapshot. Complete means every originally selected source is still allowed and within that last-known window; partial means some; stale means none. Empty items with complete coverage means no eligible result in this selected corpus, not that no news exists. A later uncached query can observe newer poll state.

The deterministic service uses ranker version `metadata-v1`, a one-minute cache and one-minute work lease, with no provider reservation or invocation. Cache hits, idempotency replay and snapshot reads do no acquisition or reranking. Reads preserve stored order but suppress currently revoked sources, including sources removed only from preferences, and warn about access and category gaps. Disabled feeds remain private not-found. Retained snapshots warn when their cache window has expired; expires_at is not a source-freshness promise. Failed work keys stay terminal under the existing coordination contract. Poll-state changes without new articles become visible to newly computed snapshots after the bounded cache expires.

## Migration, validation and limits

Migration 6 adds bounded preference/details JSON columns, a preference revision trigger and an effective-age index. It is additive and forward-only. Existing minimal snapshots remain readable through the older storage seam but cannot be projected as rich evidence by the new service: it returns unavailable rather than inventing timestamps or coverage. Old binaries reject schema 6; rollback requires a coherent pre-migration backup or forward fix. No live database is migrated by tests or repository checkout.

`make check race vuln` includes real SQLite/FTS isolation, saved preference ordering, shared publisher limits, duplicate fallback, age/exclusion/candidate bounds, unknown dates, successful-poll coverage ageing, immutable replay/restart, revocation, cancellation, atomic finalization failure and terminal-key tests. `make test` also runs `scripts/check_retrieval.py`, which validates a real maximum-sized service response against the unchanged JSON schema. The existing upgrade matrix now covers populated schema 1–5.

[Authored labelled fixtures](../testdata/evaluation/retrieval.json) cover each personal interest plus PHP and Go project contexts; runtime tests assert exact expected selection and at least 80% labelled precision for those small cases. The mixed-digest integration fixture separately labels the expected five selections and fallback conflicts. These are deterministic regression evidence for review, not user-labelled real-news usefulness. The owner's per-interest/mixed-digest review over two weeks, excluded-relevant review and actual Pi latency/RSS/retention/recovery gates remain open. Passing synthetic labels cannot establish representative First Nations coverage or publisher independence.
